# AES-128

AES-128 keeps only 64 bits of security against Grover's algorithm, half of
what it has today. Of everything Shorwatch reports, this is the mildest
finding, and the one most often misread.

## What it is

AES with a 128-bit key. It is the default in many libraries and the fastest
variant, and nothing is wrong with it classically.

## Why it matters

Finding a key among N possibilities takes a classical computer on the order of
N tries. Grover's algorithm needs only about the square root of N. A 128-bit
key has 2^128 possibilities, so Grover needs about 2^64 quantum iterations.
Doubling the key to 256 bits restores the margin (2^128), which is why the
usual advice is AES-256.

It is not a break. Two things keep it from being one:

- Grover does not parallelize well. Spreading the search over k machines
  speeds it up by only the square root of k, not by k. The real cost of
  attacking AES-128 is much higher than 2^64 operations suggests.
- NIST still accepts AES-128. It uses AES-128 as the yardstick for its lowest
  post-quantum security level (category 1: breaking a scheme must cost at least
  as much as searching an AES-128 key). Its post-quantum FAQ says that "it is
  quite likely that Grover's algorithm will provide little or no advantage in
  attacking AES" and that "AES 128 will remain secure for decades to come".

So why report it? Because long-lived secrets are where a smaller margin
hurts, and because security frameworks that target the post-quantum
transition, such as the NSA's CNSA 2.0, require AES-256.

## How urgent

Low. This is the lowest severity Shorwatch assigns. It is a "next time you
touch this" item, not an incident.

It does grow with the secret's lifetime. Data that has to stay confidential for
decades is a better argument for AES-256 than data that is gone next week.

## What to do

Use 256-bit keys. Unlike the public-key findings, this is usually a parameter
change: same API, same IV length, same authentication tag.

For the simplest case, a literal `KeyGenerator.init(128)` in the JCA,
Shorwatch suggests the exact edit, and tools that read SARIF can apply it. A
value written in another form (`0x80`, `128L`) or coming from a constant is
reported without a suggested edit.

The catch is the keys you already have. Existing 128-bit keys, whether in a
keystore, a database or shared with another service, don't change by
themselves. Data encrypted with them stays encrypted with them. A migration
means generating new keys, re-encrypting data and distributing the keys,
so plan a key rotation alongside the code change.

## Where Shorwatch finds it

- **.NET:** `KeySize = 128` on `Aes`, `AesManaged`, `AesCryptoServiceProvider`
  and `AesCng`. `Aes.Create()` alone is not reported: its default key is 256 bits.
- **JCA:** `KeyGenerator.init(128)` and size-pinned transformations such as
  `AES_128/GCM/NoPadding`.
- **Cloud KMS:** AWS `DataKeySpec.AES_128` (envelope encryption data keys) and
  Azure Key Vault's `A128*` algorithms.
- **Tink, OpenPGP, XML Encryption (Santuario) and OpenSAML:** their 128-bit AES
  templates and constants.
- **TLS:** cipher suites with a 128-bit key, in IANA form (`..._AES_128_...`)
  and OpenSSL form (`ECDHE-RSA-AES128-GCM-SHA256`, `AES128-SHA`), in code,
  in OkHttp's `ConnectionSpec` and in Spring Boot cipher lists.
- **JWT/JOSE:** `A128GCM`, `A128CBC-HS256` and the `A128KW` family have
  [their own page](jose-aes-128.md).

Shorwatch checks what kind of generator it is: a `KeyGenerator` created for
`HmacSHA256` and initialised with 128 is not an AES key and is not reported.
If the generator comes from somewhere Shorwatch cannot see (a parameter, a
field), it is reported anyway, since `init(128)` is almost always AES.

## False positives and limits

- AES-128 in a TLS cipher list is also reported once for the key size,
  alongside the key-exchange finding. The key exchange is the bigger problem.
- `TLS_AES_128_GCM_SHA256`, the TLS 1.3 suite every implementation must
  support, is reported too. The finding is about the key size, not about TLS
  1.3 being a bad choice.
- A GCM tag length is not a key size: `new GCMParameterSpec(128, iv)` is not
  reported.
- The size of a key built from bytes (`new SecretKeySpec(new byte[16], "AES")`,
  or one derived from a passphrase) is not visible. Only sizes written as
  parameters are.
- If the security requirement really is short-lived data, you may reasonably
  decide to accept AES-128. The finding is there so that it is a decision.
